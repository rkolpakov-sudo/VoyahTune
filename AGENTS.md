## 1. АБСОЛЮТНЫЕ АКСИОМЫ (нарушение = немедленная остановка работы)

1. **Эталон исправности** — текущая реализация **функциональна и работает** на **Voyah Free Sport+ 2026** (OD Sport+ 26). Это **единственная целевая машина** проекта. Любое изменение = риск регресса на подтверждённом стенде.
2. **Сохранение работоспособности > всё остальное.** Запрещён рефакторинг «ради чистоты». Изменения кода только ради: (а) улучшения функционала, (б) исправления задокументированного бага, (в) устранения риска безопасности — и только после **явного** согласования с пользователем.
3. **Постоянная сверка с справочниками:** `Docs/CAN-команды.odt`, `Docs/can.pdf`, `readme.md`, `hownews.md`, `Packaging/README.md`, поведение существующего кода. Никаких изменений CAN/policy/транспорта/бута «по интуиции».
4. **Нет полной уверенности → не менять, задать вопрос.** Молчаливое допущение недопустимо.
5. **Тройной анализ** перед каждым изменением файла:
   - (1) Назначение, все точки вызова, контракты;
   - (2) Impact на hot-path (CAN, boot, установка, IPC между Native ⇄ RestoreMode);
   - (3) Сверка с эталонным поведением Sport+ 2026 и справочниками.
   Ответ включает: что меняется, почему, какие есть риски, что **не** покрыто уверенностью.
6. **`origin` (github nexron171/VoyahTune) — уже протестированный на автомобиле код.** Ему можно доверять: он **не может навредить автомобилю**. **Извлечение данных/кода из `origin` всегда допустимо** — в том числе из hot-path-файлов (`vd_bypass.js`, `SetModesService`, JNI и т.п.). Отдельное live-тестирование изменений, пришедших из `origin`, **не требуется**; ограничения п. 2.3 относятся к локальным изменениям, которых нет в `origin`. *(Директива пользователя: 2026-09-25.)*

**Это не программный эксперимент.** Ошибка может навредить автомобилю и повлечь тяжёлые последствия для пользователей.

## 2. ПРАВИЛА РАБОТЫ

### 2.1. Что можно без отдельного код-согласования
- Чтение кода/документации, анализ.
- Создание/правка **документации** (`docs/**`, README-черновики) — без изменения поведения ПО.
- Тестовые/проверочные скрипты **read-only** (не пишут в ГУ, не трогают install).
- Ведение `docs/agent/HISTORY.md` (журнал сессий).

### 2.2. Что ТОЛЬКО после явного «делай» по пункту
- Любое изменение `.java`, `.js` (Frida), `.sh`/`.bat` (установщики), `.xml` (манифесты/whitelist), `.rc`/`.bin`, Gradle.
- В том числе «быстрые security-fix» из аудита (R3, R4, R9, R12…) — **не начинать самому**.
- Фазы 3–6 плана — по согласованию, **по одному пункту**.

### 2.3. Категорически не трогать без отдельного целевого проекта и живых тестов на авто
| Объект | Причина |
|--------|---------|
| `CanSender`, `ApplyEngine`, `*CanTransport`, `*CanPolicy` | Hot-path CAN → риск для автомобиля |
| `native-lib.cpp`, JNI (`cis_can_control_bytes`) | То же |
| `vd_bypass.js`, `load.bin`, `voyahtune.load.rc`, `voyahtune.load.sh` | system_server / бут → крэш = потеря ГУ |
| Порядок и логика фаз `full/install.sh` | Атомарность, две перезагрузки |
| Вынос в AIDL, «модульность», minify/R8 release без keep-правил | Не даёт функции, ломает проверенное |
| API `RECEIVER_EXPORTED` «вслепую» | Сначала подтвердить фактический API ГУ (риск R20) |

### 2.4. Порядок фаз плана
Фаза 0 ✅ (аудит, 2026-09-23) → **Фаза 1** (документирование) → **Фаза 2** (тесты + матрица) → согласование пунктов Фазы 3 → по одному PR → прогон чек-листа на Sport+ 2026 → далее.

### 2.5. Перед завершением сессии (обязательно)
1. Обновить `docs/agent/HISTORY.md` (что сделано, что не сделано, открытые вопросы).
2. Если менялся код — указать файлы и как проверять.
3. Не коммитить/не пушить без явной просьбы пользователя.
