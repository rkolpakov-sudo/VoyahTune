# Участие в разработке VoyahTune

## Обязательно перед любой сессией

1. **`AGENTS.md`** — аксиомы, красные линии, шаблон тройного анализа.
2. **`docs/agent/REFACTOR_PLAN.md`** — единый план и статус.
3. **`docs/agent/HISTORY.md`** — что уже сделано.
4. **`docs/agent/PROJECT.md`** — архитектура и IPC.

## Что можно без отдельного код-согласования

- Чтение/анализ, документация `docs/**`, README, read-only тесты, `HISTORY.md`.

## Что только после явного «делай» по пункту

- Любой `.java`, `.js` (Frida), `.sh` / `.bat`, `.xml`, `.rc` / `.bin`, Gradle.
- Security-fix из аудита (R3, R4, R9, R12…).
- Фазы 3–6 плана — **по одному пункту**.

## Чего не трогать без отдельного проекта + живых тестов

- `CanSender`, `ApplyEngine`, `*CanTransport`, `*CanPolicy`
- `native-lib.cpp`, JNI
- `vd_bypass.js`, `load.bin`, `voyahtune.load.rc/.sh`
- Порядок фаз `full/install.sh`
- Apollo master, `MSG_*` числа, CAN-валидация `%31`
- `RECEIVER_EXPORTED` «вслепую» (сначала `adb shell getprop ro.build.version.sdk`)

## Тройной анализ (перед правкой)

Формат — `AGENTS.md` §4: что меняется / impact / сверка со справочниками + РИСКИ / НЕ ПОКРЫТО / ПРОВЕРКА / СОГЛАСОВАНИЕ.

## Стиль кода

- Не добавлять комментарии «для красоты» в существующий код без задачи.
- Следовать локальным паттернам (Messenger `MSG_*`, policy-классы, shell-идиомы установщика).
- Не «лечить» архитектуру (ARCH-*) молча — описывать и ждать решения.
